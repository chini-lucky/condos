# Condos — agreed requirements

Agreed 2026-10-20. This records the product and implementation decisions from the planning session. [tickets.md](tickets.md) maps the scope to the 17 approved GitHub issues. The [design specification](design/README.md) and [prototype](design/prototype.html) are visual and interaction references; their hardcoded data, random positions, defaults and in-memory mutations are not production requirements.

## Purpose and access

- A private Bangkok rental-offer shortlist for one admin. Each record represents an offer from an agent; duplicate building names and multiple offers for the same apartment are allowed.
- Manual entry initially, with an optional source URL. No imports, chat extraction or external listing integrations.
- React and TypeScript frontend with Supabase database, Auth and private Storage. Create a dedicated Condos Supabase project in the Chini Lucky organization, independent of Lola.
- Visible username `chini-lucky`, internally mapped to `chini-lucky@condos.invalid` for Supabase password authentication, following Lola's approach. No real email is needed.
- One provisioned account; no registration, roles, invitations or user directory. Restrict database and storage access to the specific admin account ID, not all authenticated users.
- Persist/refresh sessions and provide logout. Password recovery is through Supabase administration; no in-app recovery flow.
- The generated long password is held in an owner-only local text file outside the repo for transfer into a password manager. Never publish it or privileged backend credentials in code, logs, tickets or browser assets. These planning artifacts do not provision the account.

## Offers and unknown information

- Only a nonblank name is required when creating or editing an offer. All user-entered rental, location, contact and appointment fields are optional and clearable. System IDs, timestamps and default Pending status are generated by the application.
- Optional facts: condominium/townhouse type, monthly THB rent, walking metres, direction/bearing, square metres, beds, floor, station, agent name/company/phone/LINE and source URL.
- Missing values remain unknown. Never fabricate rent, distance, size, beds, floor, agent details, map bearing or chat provenance.
- Washer, garden, pool and microwave distinguish unknown, present and absent. Extra facilities are optional named removable chips.
- Keep agent information on each offer rather than in a shared agent directory. Contact actions include Call, Open LINE and Copy when the needed value exists.
- Record creation and update timestamps. Current facts plus editable notes are sufficient; no full change-history system.

## Stations, distance and map

- Include every station on BTS Sukhumvit (Khu Khot–Kheha), BTS Silom (National Stadium–Bang Wa) and MRT Blue, including its full loop and Lak Song branch. Reference official BTS and BEM sources and record verification dates. Other rail lines are outside scope.
- Start from the official-map-derived schematic design, extending it to full coverage. Preserve the line colors, interchange connectors, river orientation, names without visible station codes, and BTS/MRT badges.
- Official references: https://www.bts.co.th/eng/routemap.html and https://metro.bemplc.co.th/MRT-System-Map?lang=en .
- An offer can have one selected station, or none. Unassigned offers are always accessible through an Unassigned list.
- Walking distance and direction are separate optional manual inputs. Render a positioned pin only when station, distance and direction are all known. Otherwise a station-assigned offer remains in its station list and count.
- Estimate walking time at 80 metres/minute and label it as estimated. The schematic location is not a measured walking route.
- Implement drag/pinch/wheel/double-click and keyboard navigation, desktop zoom controls, semantic zoom and nearest-station navigation from the design.
- Include 400/800/1200m rings, focused/nearest station labels and collision-aware callouts. Synchronize cards and pins, including accessible touch/keyboard use.
- Follow the approved overview/station/unit/add/edit navigation, back controls, Escape behavior, direct links, desktop collapsible panel and mobile draggable sheet.

## Status, appointments and notes

- Statuses: Pending, Available, Viewing, Rejected. New offers start Pending; the admin can freely change status.
- Available means agent-confirmed availability; Viewing means a viewing is arranged; Rejected means ruled out, including an unavailable offer.
- Pending can have an optional waiting-on message; Rejected can have an optional reason; Viewing can have an optional appointment. None becomes mandatory under the name-only creation rule.
- One current appointment per offer, entered/displayed in Bangkok time and stored unambiguously. Support booking, rescheduling and clearing. Past appointments never automatically change status.
- No calendar integrations, reminders or appointment-history subsystem initially.
- Rejected offers stay visible at full strength except for ordinary filter effects. Status colors belong to labels, not the unit dot.
- Notes form a persistent timeline with creation/edit timestamps, entry count, inline edit/save/cancel, and confirmed deletion. Blank notes are rejected; no fictional initial note is generated.

## Photos

- Accept JPEG, PNG, WebP and HEIC. Photos are optional. Maximum 20 attached photos per offer and 10 MB per source file; backend enforcement must cover count and stored-object limits as well.
- Convert uploads to displayable JPEG, with orientation preserved, a maximum 1600px longest side and quality 0.8 as the initial Lola compression baseline. Do not upscale. Remove embedded location metadata; never upload an undecodable original as a fallback.
- HEIC must convert reliably on supported browsers rather than rely only on native decoding. Clearly report unsupported or failed conversions while preserving form input.
- Private Storage and temporary signed URLs; restrict reads/writes to the admin. Handle URL expiration without making the bucket public.
- Provide carousel/dots, deterministic ordering, cover selection and confirmed individual deletion. Empty offers show neutral placeholders, not sample photos.
- Make upload/orphan/deletion cleanup retryable and observable across partial failure and concurrency. Keep metadata/order/cover consistent with actual attachments.

## Filters and presentation

- Four facility toggles, property-type selection and a THB 10,000–35,000 slider in 500 steps. Top value means Any, including rents above 35,000. Neither or both types selected means all types.
- Unknown values do not satisfy an active corresponding filter. Without an active filter, incomplete offers remain browseable.
- Type/rent misses leave the station list; facility misses remain in a dimmed separate group identifying what is absent or unknown.
- Update map opacity, matching station counts, station-card totals, lowest known matching rent and filter summary consistently. Keep zero-match station cards dimmed. Supply both no-data and no-match empty states.
- Follow the design's Instrument Sans typography, colors, icon treatment, prices/distances, responsive layouts, contact card and form behavior, while accommodating the agreed incomplete-data and management flows.

## Deletion, reliability and implementation

- Moving an offer to Trash hides it from normal map/list/filter results and retains its facts, notes and photos. Restore returns it to its station or Unassigned. Trash has no automatic expiry; Rejected is separate.
- Permanent deletion is explicitly confirmed from Trash and removes associated notes/photo metadata/storage objects with durable retryable cleanup.
- Refresh when returning to the app without erasing drafts. Report successful saves only after backend confirmation and preserve input on failure.
- Detect stale edits server-side; show conflicts instead of silently overwriting changes from another device. Apply suitable concurrency checks to offers, notes and photo organization. Real-time synchronization is deferred.
- Build production React components with clear responsibilities and a data-access boundary; do not paste or embed the prototype as the application.
- Version database changes through migrations. Supply reproducible local Supabase development/test setup, keep production isolated and protect secrets.
- Each implementation slice includes appropriate type/lint/format checks and meaningful behavior, database/storage authorization and browser tests. Include keyboard/touch usability, loading/empty/error/success states and reduced motion.
- Automate controlled frontend/backend deployment, link implementation PRs to their issues and record validation evidence. The final release verifies requirement coverage, integrated behavior, desktop/mobile design and hosted security.
- No application implementation, Supabase provisioning or deployment is performed by the ticket-publication task.
