# Private offer photos

The browser validates JPEG/PNG/WebP signatures and source size (10 MiB), decodes with source orientation, and rasterizes fresh pixels to a white-backed JPEG at quality 0.8, longest side 1600, without upscaling. Failed decoding never returns source bytes. `src/photos/process.ts` exposes `processPhoto(File)` and `encodePhoto(ImageBitmap)` so HEIC can later supply already-oriented decoded pixels through the same encoder.

`photosRepository` is the Supabase boundary. The browser reserves all selected slots atomically, keeps selection indices, and converts/uploads one image at a time to bound phone memory. It retains failed files for retry and saves successful siblings. Every path exists durably before Storage writes; a lost network response cannot create an untracked path. The uploader retains its request UUID until reservation succeeds and keeps each selected file’s reservation identity after uncertain upload responses. It reconciles ready attachments before reserving a retry, so an attachment whose success response was lost is confirmed rather than duplicated. A server retry after Storage success but before finalization reads and validates the already-stored object and records that object’s actual dimensions/size. Sources are never sent to Storage. The server can verify uploaded/stored sizes, but cannot independently know a source file's original pre-conversion size.

`upload-photo` requires an actual admin user JWT, reads a live reservation through that identity, enforces bounded request bytes and JPEG dimensions, decodes using pinned `jpeg-js@0.4.4`, then re-encodes actual pixels without EXIF/GPS or trailing metadata. This small pure JavaScript decoder avoids a large native/WASM runtime. Both baseline and progressive JPEG decoding are supported by the decoder. Header dimensions are checked before decoder allocation; decoding has 3 MP / 64 MiB allocation limits. Storage accepts JPEG only, with a separate 10 MiB object cap. Browser writes cannot bypass ingestion. Authenticated accounts other than the provisioned UUID cannot reserve, read metadata, sign, upload, mutate or invoke cleanup.

Reservations and finalization lock the offer first. Uploading + ready assets consume the server's 20 slots. Immutable UUID paths, a request UUID and persistent selection positions make retries idempotent and completion order irrelevant. Photo mutations use `photo_revision`, keeping fact-edit `version` independent. The initial cover is the first selected ready photo. The carousel and card display consume ready assets only. Signed URLs live only in React memory, renew 30 seconds before their five-minute expiry or after an image failure, and disappear on logout/unmount.

## Cleanup and extension contract

`photo_assets` tombstones and `photo_cleanup` jobs must survive permanent deletion. Do not delete asset rows or reuse object keys. An offer FK SET NULL trigger marks detached assets deleting and inserts cleanup work in the same transaction. `cancel_photos(uuid[])` cancels only uploading assets; completed siblings remain. The later Trash command should cancel uploading assets under its existing offer lock and leave ready attachments/order intact. `finalize_photo` rechecks the offer, state and lease; a cancelled/deleted/expired upload can never reattach.

`claim_photo_cleanup` expires abandoned 15-minute reservations, reconciles read-only Storage metadata against missing/deleting assets, reopens completed jobs when a late object appears, and leases bounded jobs with SKIP LOCKED. Workers remove bytes through the Storage API, verify absence through a successful folder listing, then acknowledge the exact lease. A crashed worker's two-minute lease expires; a failed delete records an admin-readable error and exponential retry time (maximum one hour). Repeating a completed removal is harmless. Never treat a forbidden/error response as evidence of absence. The worker never claims a ready referenced asset. `photo-cleanup` ignores caller-supplied paths and accepts only the dedicated scheduler secret or an admin JWT. It compares the secret in constant time and rejects missing/empty values.

The admin UI exposes pending/failed cleanup counts and a retry action. Scheduled retries remain necessary even if the app never opens again.

## Controlled production setup

Migration `202610200010` installs private tables/bucket/policies and a one-minute pg_cron/pg_net job named `condos-photo-cleanup`. The job remains inert until **both** Vault secrets exist:

- `condos_photo_cleanup_url`: `https://sthwmiesffowystewspf.supabase.co/functions/v1/photo-cleanup`
- `condos_photo_cleanup_secret`: a freshly generated high-entropy dedicated worker secret, identical to Edge environment `PHOTO_CLEANUP_SECRET`.

Trusted deployment tooling must set/update the two Vault values (use `vault.create_secret` / `vault.update_secret` with values supplied through trusted input), set the matching Edge secret using an owner-only env file and `supabase secrets set --env-file ... --project-ref sthwmiesffowystewspf`, and deploy both functions from this checkout. Keep `verify_jwt = false` for these two self-authenticating endpoints. No service key, worker secret, decrypted Vault value, signed URL or password belongs in logs, SQL command text shown in chat, frontend assets or Git. Scope credentials to the dedicated Condos project. The SQL cron command contains only Vault names, not credentials. Production setup is handled by the controlled deployment pipeline/operator, not test tooling.

After deployment, inspect safe job status (`cron.job_run_details`), Edge response status, and admin-visible queue attempts/errors; create a deliberate disposable cancelled-upload fixture and verify that its bytes disappear through scheduled processing without invoking the admin retry endpoint. A SQL cron success alone means pg_net accepted the request, so also verify the HTTP response and physical object absence. Local `scripts/verify-local-photo-scheduler.ts` performs that end-to-end proof using disposable resources. If a secret rotates, update Vault and Edge together; queue jobs persist and retry after configuration is repaired.
